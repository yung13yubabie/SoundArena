# ADR-0031:Header 次要連結對比度不足(真實瀏覽器測試發現)

原始稽核報告的 Accessibility 章節誠實標記「47/100 不是因為找到大量 WCAG failure,而是沒有足夠的 system-level accessibility evidence」——報告本身沒有做真實瀏覽器測試。這次用 `claude-in-chrome` 對正式站首頁做真實對比度計算,補上報告做不到的驗證。

## 方法

在正式站首頁注入 JavaScript,對頁面上每個文字節點:取得 computed `color`,往上遍歷祖先元素做正確的 alpha 合成算出「有效背景色」(不是天真地拿第一個非透明背景就當數值——半透明疊層需要跟更下層的顏色混合,第一版腳本沒做這件事,算出「好友測試賽」卡片標題對比度只有 1.17 這種明顯不合理的假象,修正合成邏輯後這個假陽性消失),依 WCAG 2.1 公式算對比度,對照文字大小決定門檻(≥18px 或 ≥14px+bold 用 3:1,其餘用 4.5:1)。

## 發現

Header 的「更新記錄」「意見回饋」連結,以及 Discovery 頁的「看看主辦人」連結,共用 `text-ink-faint`(`#7d6a62`)這個顏色 token,在深色背景(`#130b09`)下實測對比度 **3.81:1**,低於 12.5px 文字需要的 4.5:1 門檻——是真實、可驗證的 WCAG AA 失敗,不是猜測。

## 修法

只改這三處(桌機版 + 手機選單版共 5 個 `<Link>`)的顏色 class 從 `text-ink-faint` 改成 `text-ink-dim`(`#b9a89f`),不動 `--color-ink-faint` token 定義本身——這個 token 在其他非互動的輔助文字情境還在用,直接改 token 值風險是牽動未稽核過的其他畫面。`text-ink-dim` 對同一個背景色的對比度約 8.48:1,遠超門檻。

## 驗證

改動前用真實瀏覽器對正式站計算過一次(確認問題存在),部署後用同一支腳本(alpha 合成邏輯不變)再測一次正式站,確認三處連結的對比度都已經在門檻之上,且沒有新增其他低於門檻的文字節點。

`tsc`/`eslint`/`build` 全程乾淨,已 commit、push、`vercel --prod` 上線。
