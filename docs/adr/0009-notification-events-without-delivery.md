# 通知系統先做「事件記錄」,不做真的寄信/推播

SPEC.md 第 6 節早就定案通知系統的訂閱範圍鐵律(報名才訂閱、可取消)跟觸發時機清單,但寄信服務商一直沒選定(「尚未決定寄信服務商...先記錄需求」)。這輪使用者要求把通知系統排進待辦,用 `AskUserQuestion` 問清楚兩個分岔,不是自己猜:

1. **Email 寄信服務商**:使用者目前沒有已備妥 API key 的服務商(Resend/SendGrid 都沒有)——確認「先不要做真的寄信」,架構先把訂閱/觸發邏輯建完整,實際寄信呼叫留白。
2. **Discord 通知方式**:私訊,不是伺服器頻道——每則通知都精準對應到特定使用者(SPEC.md 設計原則),頻道廣播不符合這個精神。

## Considered Options

- **方案 A(採用)**:建立 `notification_events` 表,記錄「誰、為了什麼事、該收到什麼內容、透過什麼管道」,狀態預設 `pending`。**不**額外裝一個 `console.log` 假裝已經在寄信——`pending` 狀態本身就是誠實反映「系統知道該發什麼,只是還沒有 sender 真的送出」,不需要用診斷輸出去模擬一個尚不存在的寄信行為。之後接上真的寄信服務商,只要新增一支背景程序把 `pending` 的事件實際送出、改狀態成 `sent`/`failed`,不用重構這輪建的架構。
- **方案 B**:等使用者真的選好寄信服務商再動工——已否決,使用者這輪明確要求現在就把這塊排進去,而且「訂閱 + 事件記錄」這一半完全不依賴寄信服務商是誰,可以先做完。
- **管道判斷方式**:讀 `auth.users.raw_app_meta_data ->> 'provider'`(Google 登入 → email;Discord 登入 → discord),不是讓使用者自己選管道——SPEC.md 原文「通知管道由登入方式決定」,不是可勾選設定。

## Consequences

- 目前只有兩個真實觸發點接上了:報名成功(`registerForCompetition`)、投稿送出(`submitEntry`)。SPEC.md 第 6 節列的其餘觸發時機(逾期未投稿提醒、投票開始、晉級開放投稿提醒、該輪淘汰/晉級結果、最終名次公布)這輪**沒有**實作——這些要嘛需要排程機制(pg_cron,「時間到了」觸發,不是使用者操作觸發),要嘛需要 Organizer 端多一個「確認發送」的按鈕(SPEC.md 要求淘汰/晉級結果要人工審核過才發)。這是刻意的範圍縮減,不是遺漏,留在 HANDOFF.md 待辦清單。
- `/status` 頁新增「通知」區塊(顯示 `notification_events` 列表)跟每筆報名的訂閱開關——即使實際寄信還沒接上,使用者在站內就看得到「系統認為該通知我這些事」,這本身也是一種站內通知中心,不完全依賴外部管道才有用。
- Email 通知目前只有 Google 登入的使用者收得到(見 CONTEXT.md NotificationEvent 詞條的 channel 判斷邏輯);email/password 測試帳號、未來的 LINE 登入(如果真的申請下來)不會建立任何通知事件——這是 SPEC.md 原有規則的直接結果,不是這輪新增的限制。
