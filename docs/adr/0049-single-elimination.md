# ADR-0049:單敗淘汰(single_elimination)

賽制細節填空最後一塊(雙敗淘汰留給下一批)。用 `mattpocock-skills:grilling` 跑三輪收斂設計。

## 設計(grilling 三輪收斂的決定)

1. **範圍**:只做單敗淘汰,雙敗淘汰(需要再疊加敗部規則)留到下一批——單敗的樹狀晉級架構先穩了再疊加。
2. **對戰單位**:跟循環賽一樣先只做個人,不跟隊伍分組互動。
3. **配對機制**:第一輪隨機抽籤配對,沿用循環賽剛做的隨機打散邏輯,不需要種子排名。**每一輪(不只第一輪)都重新隨機配對**,不保留固定賽事樹位置——理論上同一組對手可能在不同輪次又碰到,使用者確認這是可接受的簡化(不是傳統選手保持固定 bracket 位置的競技賽事模式)。
4. **跨輪次對應**:單敗淘汰橫跨好幾輪比賽用的「輪次」(round),不是像循環賽那樣容納在單一輪次內。主辦人自己陸續加輪次(不用一開始就算好 log2(人數) 要打幾輪),每輪都選「單敗淘汰」積木,系統看前一輪確認結果後自動配對下一輪,不另外蓋一套「賽事樹」新概念。
5. **輪空(bye)**:報名人數是奇數時(任何一輪,不限第一輪),隨機抽中一人自動晉級,不用打這一輪——不需要事先算好整座 bracket 的深度,每輪各自獨立判斷單雙數即可,比傳統競技賽事的種子輪空規則簡單很多。
6. **輸贏判定**:沿用循環賽的 `match_votes` 配對投票機制,不重新蓋一套。
7. **平手處理**:單敗淘汰不能像循環賽一樣把平手算平局(平局代表選不出誰晉級,不能兩邊都過)——「確認本輪結果」偵測到任何場次平手時,**整個拒絕確認**,列出哪些場次平手,請主辦人到既有的「本輪專屬時程」面板延長投票時間、等更多人投票後再重新確認。沒有新蓋「重新投票」機制,直接重用既有的時程調整工具。
8. **跟 elimination_percent 的關係**:不接——單敗淘汰是「輸一場就出局」,沒有%可以調,`elimination_percent` 欄位對這種輪次沒有意義,直接忽略。

## 實作

沿用循環賽批次(ADR-0048)剛建的 `matches`/`match_votes` 基礎設施,不重新蓋。唯一的結構調整:`matches.pool_id` 從 not null 放寬成可為 null——單敗淘汰不需要「分池」概念(場次數量本來就隨每輪淘汰自然減半,不像循環賽需要用分池控制單輪內 C(n,2) 場次爆炸)。

`generate_single_elimination_matches_for_round()`:觸發時機比照組隊賽/抽籤分組同一套(第一輪報名截止、後續輪次前一輪 `results_finalized_at`),把還在比賽中的人隨機打散、兩兩配對建立 `matches`(`pool_id = null`);人數是奇數時最後一人不建立場次,自然而然在 finalize 階段不會被觸及,等於自動晉級,不需要額外的輪空記帳。

`lib/singleElimination.ts` 的 `computeSingleEliminationOutcome()`:結算每場配對的票數,任何一場平手就整個回傳 `{ ok: false, tiedMatches }`,呼叫端(`judge/actions.ts` 的 `finalizeRoundResults()`)直接把錯誤訊息(列出平手場次)回傳給使用者,完全不呼叫 `finalize_round_results()` RPC,不淘汰任何人。全部場次都有明確贏家時才回傳 `{ ok: true, loserRegistrationIds }`,寫回每場 `matches.winner_registration_id`,把輸家名單傳給 RPC 套用——不套用 `elimination_percent`,單敗淘汰是獨立分岔,完全繞過既有的%淘汰邏輯路徑。

**UI**:`/admin/format` 新增 `SingleEliminationPanel`(選了單敗淘汰積木時,取代原本的 `EliminationPercentPanel`,因為那個欄位對這種賽制沒意義)。`/vote` 的配對投票偵測邏輯從只認循環賽,擴大成同時認循環賽跟單敗淘汰,兩者共用同一套 `MatchVoteList` 畫面。

## 驗證

真實 PoC(對正式 Supabase 環境):5人隨機配對正確產生2場+1人輪空、重複呼叫冪等、平手時整體結果正確回報 `ok:false` 並列出平手場次、補票打破平手後正確回報 `ok:true` 跟兩位輸家、確認結果後正確淘汰兩位輸家且輪空者維持 active、前一輪確認結果正確觸發下一輪重新配對——9/9 通過。跟循環賽同一個已知限制:`lib/singleElimination.ts` 有 `import "server-only"`,無法用 `npx tsx` 直接 import,PoC 對照真實資料庫重新實作同一套平手偵測/贏家判定邏輯驗證。`security-regression.mjs` 新增 6 項(RPC 邊界:配對含輪空、冪等、陌生人擋下、輸家 100% 淘汰、下一輪觸發——平手偵測的 TS 層邏輯已用上述真實 PoC 驗證,RPC 本身不算贏家不重複測)。`tsc`/`eslint`/`build` 全程乾淨。

**尚未驗證**:`/admin/format` 的 `SingleEliminationPanel`、`/vote` 擴大後的配對投票判斷,沒有經過瀏覽器肉眼驗證。

## 未涵蓋(刻意延後)

雙敗淘汰的敗部規則——輸一場掉進敗部、敗部內部怎麼配對、敗部冠軍怎麼跟勝部冠軍對決、要不要有「重賽」規則——是完全獨立的下一批,還沒開始設計。至此,賽制細節填空原本規劃的四種賽制(組隊賽亂數分組、月/週期累積制、循環賽、單敗淘汰)全部完成,只剩雙敗淘汰待定。
