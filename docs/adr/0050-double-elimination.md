# ADR-0050:雙敗淘汰(double_elimination)

賽制細節填空最後一塊。用 `mattpocock-skills:grilling` 跑三輪收斂設計。

## 設計(grilling 三輪收斂的決定)

1. **範圍**:只做個人賽,不跟隊伍分組互動——跟循環賽、單敗淘汰同樣的範圍限縮。
2. **跟既有 `wildcard_revival` 特殊機制積木的關係**:兩者無關。`wildcard_revival` 是還沒有任何程式碼引用的純標籤,雙敗淘汰是自己完整一套獨立設計,不共用、不重用那個標籤。
3. **勝部/敗部配對**:每一輪,0敗組(勝部)跟1敗組(敗部)**分開隨機配對**——0敗組內部隨機兩兩配對,1敗組內部隨機兩兩配對,兩組同時各自處理(不是先打完一組再打另一組)。哪一組人數是奇數,該組自己隨機抽一人輪空,不跟另一組混算。
4. **敗場的後果**:勝部場次輸的人**不淘汰**——只是敗場數變成1,下一輪換到敗部組配對,身分還是 `active`。敗部場次輸的人是第二次輸,**直接淘汰**。這個分岔要看場次屬於勝部還是敗部才能判斷,跟單敗淘汰「每場輸家都出局」不同。
5. **敗場數記帳方式**:不另外存一欄位,即時查詢「這場比賽底下所有雙敗淘汰輪次的對戰紀錄,這個人輸了幾場」算出來——避免多一份可能跟真實對戰紀錄兜不起來的重複狀態,尤其這欄位只在配對時用得到,不需要常駐。
6. **最終戰(勝部剩1人、敗部剩1人)**:不做傳統雙敗淘汰的「敗部水漲」規則(敗部出身的人如果贏了最終戰,傳統規則會因為對面是至今全勝所以要求重賽一場「真正的決賽」)。這裡簡化成**單一決定性的最終戰**,誰贏這場誰就是冠軍,不管誰是從勝部還是敗部打上來的。使用者確認接受這個簡化。
7. **平手處理、投票機制**:沿用單敗淘汰同一套——`match_votes` 配對投票,「確認本輪結果」偵測到任何場次平手就整個拒絕確認,列出平手場次,請主辦人到「本輪專屬時程」延長投票時間。
8. **跟 `elimination_percent` 的關係**:不接,雙敗淘汰的淘汰名單完全由對戰結果決定(敗部+最終戰輸家),不是%計算。

## 實作

沿用循環賽/單敗淘汰批次(ADR-0048、ADR-0049)已建的 `matches`/`match_votes` 基礎設施,不重新蓋。`matches` 新增 `bracket` 欄位(`'winners' | 'losers' | 'final'`),不只是顯示用——決定一場輸家該不該被淘汰,要看這個欄位。

`generate_double_elimination_matches_for_round()`:觸發時機比照其他賽制同一套(第一輪報名截止、後續輪次前一輪 `results_finalized_at`)。用即時查詢算出每個 `active` 報名者目前的敗場數(join 這場比賽底下所有雙敗淘汰輪次、`winner_registration_id` 不是自己的場次),分成0敗/1敗兩組,各自獨立隨機打散兩兩配對(`bracket` 分別標 `'winners'`/`'losers'`)。

**最終戰的死結 bug 跟修法**:寫這支函式時自己發現一個問題——如果只按「同組配對」的規則(每組人數 ≥2 才配對),當比賽走到只剩「0敗組1人、1敗組1人」的最終戰場景時,兩組各自都不滿2人,**不會產生任何場次**,比賽會卡死。修法是在兩組各自配對的邏輯之前,先特別判斷「0敗組剛好1人 且 1敗組剛好1人」這個情況,直接插入一場跨組的 `bracket = 'final'` 場次並提早返回,略過正常的同組配對邏輯。這個修正在推送到正式環境前就發現並修好,`security-regression.mjs` 額外驗證這條路徑真的會正確產生最終戰場次而不是卡住。

`lib/doubleElimination.ts` 的 `computeDoubleEliminationOutcome()`:結算每場配對的票數,任何一場平手就整個回傳 `{ ok: false, tiedMatches }`(跟單敗淘汰一樣,呼叫端不呼叫 RPC、不淘汰任何人)。全部場次都有明確贏家時,寫回每場 `matches.winner_registration_id`,淘汰名單只收 `bracket = 'losers'` 或 `bracket = 'final'` 場次的輸家——`bracket = 'winners'` 場次的輸家刻意不放進淘汰名單,讓他們保持 `active`,下一輪配對時透過即時查詢的敗場數自然歸進敗部組。

**UI**:`/admin/format` 新增 `DoubleEliminationPanel`(選了雙敗淘汰積木時取代 `EliminationPercentPanel`),依 `bracket` 欄位分「勝部」「敗部」「最終戰」三組顯示對戰配對。`/vote` 的配對投票偵測邏輯擴大成同時認循環賽、單敗淘汰、雙敗淘汰三種,共用同一套 `MatchVoteList` 畫面(場次沒有 `pool_id` 時公開頁面顯示通用的「淘汰賽對戰」字樣,不特別標 bracket——那個細節留在主辦人視角的 `DoubleEliminationPanel`)。

## 驗證

真實 PoC(對正式 Supabase 環境,`lib/doubleElimination.ts` 有 `import "server-only"` 無法用 `npx tsx` 直接 import,對照真實資料庫重新實作同一套平手偵測/分岔判斷邏輯驗證):一場勝部場次平手時整輪正確回報 `ok:false`;勝部/敗部/最終戰三場都決出勝負時,淘汰名單正確只含敗部+最終戰輸家、不含勝部輸家,且贏家正確寫回 `matches.winner_registration_id`——3/3 通過。

`security-regression.mjs` 新增 9 項(RPC 邊界):3人單一比賽跑完整4輪的敘事——第1輪奇數配對含輪空、重複呼叫冪等、陌生人擋下確認結果、確認結果後勝部輸家不淘汰;第2輪0敗組配對正確排除1敗組(組員身分逐一比對,不是只比數量);第3輪1敗組配對正確、確認結果後敗部輸家真的被淘汰;第4輪驗證最終戰死結 bug 修法確實生效,正確產生跨組 `bracket='final'` 場次而不是0場卡住。`tsc`/`eslint`/`build` 全程乾淨。

**尚未驗證**:`/admin/format` 的 `DoubleEliminationPanel`、`/vote` 再次擴大後的配對投票判斷,沒有經過瀏覽器肉眼驗證。
