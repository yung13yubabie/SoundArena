# ADR-0045:淘汰配額自動化(通用機制)+ 組隊分組改成「填組數、均分打散」

賽制細節填空第二批,直接建在 ADR-0044(組隊分組小地基)上面。使用者對回報的組隊分組設計提出修正,經過多輪 grilling 收斂成一個比原計畫更通用的機制。

## 設計轉向的過程

1. **分組演算法**:原本「每隊固定人數,人數除不盡最後一隊較少」不是使用者要的。改成「主辦人填這輪要分幾組(上限5),系統把還在比賽中的人均勻分配到這幾組,餘數打散到前面幾組」(例如14人分3組→5、5、4,不是4+4+4+2)。
2. **淘汰配額**:使用者要求「先確認淘汰人數,剩餘人數才下去分組」,淘汰人數「按報名截止當下人數對照輪次表分配」。追問「這張表怎麼填」後,使用者澄清:與其做一張人數對照表(報名人數會落在哪個區間不可控),不如**每輪填一個淘汰百分比**,套用在**該輪還在比賽中的即時人數**上(不是報名截止當下的原始總人數)——這樣不管實際報名多少人都能算,不需要預先窮舉區間。
3. **自動化程度**:再追問這個百分比算出來的人數要怎麼影響淘汰,使用者明確要求**系統自動淘汰分數最低的那個百分比人數**,不是給主辦人一個建議數字讓他自己點——這推翻了最初建置 `/judge` 時(見 HANDOFF.md 08-16 深夜第三輪)記錄的設計理由「系統只算出排名給你看,由你決定誰淘汰,不是自動抓最後幾名就淘汰」。查證後確認 SPEC.md 本身沒有明文規定淘汰決定必須人工進行——第6節「淘汰結果...發送前需經人工審核確認」講的是**通知發送**要有人工緩衝,不是淘汰決定本身;而目前系統也還沒有「該輪淘汰/晉級結果」這個通知事件類型,所以這次改動跟 SPEC.md 白紙黑字沒有直接衝突,只是推翻了先前一份程式碼註解裡記錄的實作理由。
4. **機制範圍**:最後確認這個「填%、自動淘汰墊底」不是專屬於某個賽制積木,而是**通用淘汰機制**——單敗淘汰、雙敗淘汰、循環賽、月/週期累積制這些標籤之後都共用同一套,不需要各自重寫一份淘汰邏輯。這大幅縮小了「賽制細節填空」剩餘項目的實際工程量。

## 實作

**淘汰配額**:`rounds.elimination_percent`(nullable numeric,不綁定任何 format_block)。排名計算刻意留在 Next.js 端做(`judge/actions.ts` 的 `finalizeRoundResults()`,重用既有的 `lib/ranking.ts` `computeRanking()`),不在 SQL 裡重寫一份排名公式——避免 `/judge`、`/results`、這裡三處算法各自漂移。抽出新的 `lib/judgeScoring.ts`(`getJudgeScoringData()`),把原本寫死在 `judge/page.tsx` 裡的評分資料組裝邏輯抽成共用函式,`finalizeRoundResults()` 才能重用同一份資料來源——**不能**沿用既有的 `get_round_scores()`/`get_round_submissions()`(那兩個 RPC 只有「比賽公開 + 投票已截止」才回傳資料,是給公開結果頁用的;確認結果這個動作在投票剛截止那一刻就要跑,而且不是每場比賽都公開,套用會在私人比賽悄悄算出「沒人被淘汰」)。

沒投稿的 active 報名者視為這輪 0 分排在墊底,同分用 `registration_id` 排序當穩定 tiebreak。`finalize_round_results(p_round_id, p_eliminate_registration_ids)` RPC 加了冪等保護(已確認過的輪次不能重算,不然重複呼叫會拿「上一次淘汰完、人數已變少」的即時人數重算百分比,多淘汰一批不該淘汰的人)——RPC 只負責驗證權限/時間/套用淘汰名單/鎖定,不重算排名,信任呼叫端(跟 `set_registration_eliminated()` 同一套信任模型:有 review 權限就能標記任何人淘汰,這裡沒有加嚴)。名單裡混進不屬於這場比賽或已經不是 active 的 id,安靜忽略不報錯。

`/judge` 的既有手動「標記本輪淘汰」按鈕保留——finalize 前的手動標記會先把人移出 active 池,縮小自動計算的分母,兩者自然疊加(手動當例外覆蓋,自動補足剩下的百分比),不需要額外的互斥邏輯。

**組隊分組**:`round_format_blocks.config` 的 key 從 `team_size` 改成 `group_count`(上限5,未設定預設2組——這是我單方面訂的軟性預設,同 ADR-0044 的 team_size=3 一樣未經使用者逐字確認)。`form_team_groups_for_round()` 的分組迴圈改成 `v_total / v_group_count` 取整數當基礎組大小、餘數平均分給前 N 組各加 1 人。

## 驗證

真實 PoC(11/11,對正式 Supabase 環境):7人分3組→3、2、2 驗證均分打散正確;group_count 超過上限(99)被 DB 層夾在5;淘汰配額用真實票數製造排名(8人設25%→floor=2人),驗證剛好淘汰墊底2人且 `eliminated_in_round_id` 正確;冪等保護擋下重複確認;淘汰名單混進別場比賽的 id 安靜忽略;投票未截止/陌生人呼叫都正確被擋。`security-regression.mjs` 新增/修改共 10 項,48/48 通過。`tsc`/`eslint`/`build` 全程乾淨。

**尚未驗證**:新增/改動的 UI(`/admin/format` 的「分幾組」欄位、「本輪自動淘汰」面板、`/judge` 的自動淘汰預估文案)沒有經過瀏覽器肉眼驗證,原因同 ADR-0044——沒有現成登入 session。

## 未涵蓋(刻意延後)

「該輪淘汰/晉級結果」這個 SPEC.md 第6節已經規劃、但系統目前還沒實作的通知事件類型——等真的要做這個通知時,要記得套用第6節「發送前需經人工審核確認」這條規則(通知本身要有人工確認緩衝,即使淘汰決定已經自動算完)。Discord 頻道系統(建立比賽自動開頻道、報名自動加入)是完全獨立的下一批,不在這批範圍內。
