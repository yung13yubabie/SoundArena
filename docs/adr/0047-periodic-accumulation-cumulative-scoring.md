# ADR-0047:月/週期累積制——分數逐週期累加

賽制細節填空,接續 ADR-0045 的淘汰配額機制。使用者選「根基/簡單的」開始,判斷是月/週期累積制——可以直接沿用 ADR-0045 剛做完的%淘汰機制,不像單/雙敗淘汰、循環賽要整套重蓋對戰配對邏輯。

## 設計(grilling 三題收斂)

1. **一個「週期」= 一個既有的輪次(round)**——不另外蓋新的資料結構,月/週期累積賽段就是連續好幾個輪次組成,每個輪次是一個週期,沿用既有的輪次架構。
2. **每個週期都要重新投稿**,呼應 SPEC.md 第2節「每輪皆須重新投稿」的既有規則——不開特例。分數逐週期加總,不是同一首歌從頭到尾靠好幾週期持續衝分數/衝票數。
3. **淘汰不是只在最後一個週期才發生**——每個週期「確認本輪結果」時,都依「連同之前週期加總後的累積分數」篩掉一些人,不是只看那個週期自己的分數。

## 實作

`round_format_blocks` 選 `periodic_accumulation` 這個既有的 elimination 積木(標籤本身已經存在,這批補上真的行為)。`lib/judgeScoring.ts` 新增兩個函式:

- `getPeriodicAccumulationStageRoundIds(supabase, competitionId, roundId)`:往前追溯連續掛 `periodic_accumulation` 積木的輪次(依 `round_index` 排序,遇到第一個沒掛的輪次就停),回傳這個「累積賽段」包含哪些輪次 id。不是累積制的輪次回傳 `null`,呼叫端維持原本的單輪次邏輯不變。
- `mergeJudgeScoringData(perRoundData)`:把賽段內好幾個輪次各自的評分資料,依 `registrationId`、逐個 `score_item` id 加總——同一個人在賽段裡的每個週期分數疊加起來。

`judge/actions.ts` 的 `finalizeRoundResults()` 改成:先判斷這輪是不是累積賽段的一部分,是的話抓整個賽段所有輪次的資料合併加總後才算排名,不是的話維持 ADR-0045 原本的單輪次邏輯。排名/淘汰選擇的其餘邏輯(floor(% × 活躍人數)、同分 tiebreak、`finalize_round_results()` RPC 的驗證/套用/冪等鎖定)完全不變,只有「排名要用哪些資料算」這一步分岔。

## 已知限制(刻意簡化,不是這批要解決的範圍)

`mergeJudgeScoringData()` 假設賽段內的輪次共用同一份計分規則(沒有各自覆寫)——如果賽段中某個週期的輪次有自己的 ScoringRule override,`score_item` 的 id 會跟其他週期對不上,加總會失真。這是因為每輪都可以有自己覆寫的評分規則(既有功能),但賽段內每輪各自覆寫、又要跨輪加總,兩者疊在一起會產生真正的資料一致性問題,超出這批範圍。

## 驗證

真實 PoC 兩層:①手動複製演算法邏輯對照真實資料庫,驗證核心情境(累積分數正確識別出跟「只看單一週期」不同的淘汰對象)。②用 `npx tsx` 真的 `import` `judgeScoring.ts`/`ranking.ts` 這兩支正式程式碼(不是重寫一份邏輯來測),驗證 `getPeriodicAccumulationStageRoundIds()` 對累積賽段/非累積賽段判斷正確、`mergeJudgeScoringData()` 真的把兩個週期的票數加總(3人情境:週期1+週期2票數分別是 3/19/12,加總結果精確符合預期)、依累積分數排序後找出正確的淘汰對象——4/4 通過。過程中連續抓到三個 PoC 腳本本身的錯誤(不是程式碼的 bug,是測試資料的時間/權限設定問題),每次都记录下根因才修正,不是憑猜測改。`security-regression.mjs` 新增 1 項永久回歸測試(2人2週期情境,累積分數較低者被淘汰,不是單週期分數較低者),50/50 通過。`tsc`/`eslint`/`build` 全程乾淨。

**尚未驗證**:`/admin/format` 目前沒有任何 UI 提示「這是累積賽段,分數會延續前面週期」——`EliminationPercentPanel`(ADR-0045 做的)雖然可以正常填,但沒有特別說明累積制的行為差異,使用者體驗上容易誤會成跟單一輪次淘汰一樣。這批沒有補這段文案,留給下次調整賽制頁 UI 時一起處理。
