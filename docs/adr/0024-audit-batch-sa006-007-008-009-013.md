# ADR-0024:稽核批次修復——SA-006 / SA-007 / SA-008 / SA-009 / SA-013

使用者用 `/goal` 設定「繼續進行後續的審計稽核未完成工作,可分輪分批次,到整個審計報告都完成」,授權在不需要每項都先確認範圍的情況下持續處理剩餘 findings。這是第一批,涵蓋五個獨立問題。

## SA-006:B2 刪除失敗遺失重試用的 key

`cleanupNonFinalistAudio()`(手動觸發)跟 `/api/cron/cleanup-audio`(自動排程)原本不管 B2 `deleteAudioObject()` 有沒有真的成功,都會呼叫 `clear_submission_audio()` 或直接清空 DB 的 `audio_object_key`——刪除失敗時就永久丟失重試所需的 key,私人音檔可能悄悄留在 B2 卻再也找不到。

修法:只有 B2 刪除**真的成功**才清 DB 欄位,失敗就整個跳過那一筆。key 還留著,下一輪清理(手動或 cron)因為 `planAudioRetention()` 判斷「該清的清單」時看到 `audio_object_key` 還在,會自然重新嘗試——不需要額外的 tombstone/retry 狀態表。

**驗證誠實記錄**:黑箱測試很難真的「製造」B2 delete 失敗(對不存在的 key 執行 DeleteObject 在 S3 語意上通常是 idempotent 成功,不是失敗),所以真實 PoC 只驗證了「刪除成功時正確清空 DB」這個 happy path,「刪除失敗時正確保留 key」這半段是程式碼審查層級的驗證(邏輯很簡單:`try { delete; b2Deleted=true } catch {} if (b2Deleted) { clear }`),不是端對端黑箱證明。

## SA-007:score 寫入沒有驗證 score_item 對應的 scoring_rule

`saveScore()`(judge/actions.ts)原本直接 client-side upsert `submission_scores`,RLS 的「organizer or collaborator manageable」policy 只檢查「這個 submission 所屬的比賽你有沒有 judge 權限」,沒檢查「這個 `score_item_id` 是否真的屬於這個 submission 適用的 scoring_rule」——持有合法 judge 權限的人可以把別的比賽/別的 scoring_rule 底下的 `score_item_id` 塞給任何自己能評的 submission,污染計分資料完整性。

修法沿用 registrations/votes/comments 已經在用的手法:`revoke insert, update, delete on submission_scores from public, authenticated, anon`,新增 `save_submission_score()` SECURITY DEFINER RPC,內部明確比對 `score_items.scoring_rule_id` 是否真的等於這個 submission 所屬 round(或比賽預設)實際套用的 scoring_rule_id。

真實 PoC(4/4 通過):合法評分成功並落地、跨 scoring_rule 塞入的 score_item_id 被拒絕、對沒有權限的比賽評分被拒絕(回歸)、**直接繞過 RPC 對 `submission_scores` 下 upsert 被 GRANT 層擋下**(`42501 permission denied`)——證實 REVOKE 真的生效,不是只加了 RPC 但舊路徑還開著。

## SA-008:建立比賽不是原子操作

`createCompetition()` 原本依序做 4 個獨立呼叫(insert competition → RPC create_initial_rounds → insert scoring_rule → insert score items),中途任一步失敗,前面已成功的部分不會自動 rollback。

修法:新增 `create_competition_full()` RPC,把整套「建立一場比賽」收進單一函式呼叫——一次 RPC 呼叫就是一個 Postgres transaction,任何一步 `raise exception` 全部 rollback。`slug` 的產生邏輯刻意留在 TypeScript(unicode 感知的正規表達式 + 隨機後綴),不在 SQL 裡重寫一份,原子性跟 slug 演算法是兩件不相干的事。

**真實 PoC 用注入失敗手法驗證(呼應 ADR-0015 的 TOCTOU pg_sleep() 注入延遲精神)**:寫了一支暫時診斷函式,複製同樣的邏輯但故意在「建立輪次之後、寫入 scoring_rule 之前」`raise exception`,呼叫後查詢——**連已經成功 insert 的 competition 本身都完全消失**,證明不是只有失敗那一步被擋,而是整個 transaction 真的被回滾。驗證後已移除診斷函式(`20260822080000_cleanup_diag_atomicity_temp.sql`)。

## SA-009:Switch 元件缺 accessible name/role/state

`Switch.tsx` 原本是裸 `<button>`,沒有 `role`、沒有 `aria-checked`、沒有名稱,螢幕報讀器只會唸出一個沒有名字的按鈕。7 個呼叫點(CollaboratorsClient ×2、AdminFormatClient ×2、PrivacyPanel ×2、NotificationToggle、AdminShell)全部補上必填的 `label` prop。

修法:補上 `role="switch"`、`aria-checked={on}`、`aria-label={label}`(呼叫端強制要交代這個開關的意思,TypeScript 編譯期就會擋掉漏傳)、`focus-visible` 樣式讓鍵盤使用者看得到焦點在哪。順手把觸控目標從 20×36px 調到 24×40px,符合 WCAG 2.2 AA 對最小尺寸的建議。

## SA-013:OAuth 完成後導回首頁,丟失原始目的地

`/auth/callback` 原本固定 `redirect(\`${origin}/\`)`,使用者從 `/register?competition=X` 被導去登入,OAuth 完成後不是回到原比賽,而是首頁,得重新找一次。

修法:新增共用的 `web/src/lib/loginRedirect.ts`——`redirectToLogin(next)` 統一組出 `/login?next=...`,`safeNextPath(raw)` 驗證只接受站內相對路徑(擋掉 `//evil.com`、`https://evil.com`、`javascript:...` 這類會被瀏覽器當外部導向或執行的格式,避免這個回跳目的地被拿來做 open redirect)。11 個「未登入導去 /login」的頁面(register/submit/status/vote/judge/feedback/admin/format/admin/schedule/admin/collaborators/admin/profile/admin/review)全部改用 `redirectToLogin()`,有意義的 query 參數(如 `/register?competition=X`、`/judge?c=&round=`)一併保留。`/login` 頁接受 `next` searchParam,OAuth 按鈕把它編碼進 `redirectTo`,`/auth/callback` 完成後導回這個目的地而不是固定首頁。

**驗證**:`safeNextPath` 是純函式,獨立寫了 10 組測試案例(6 種惡意輸入 + 4 種合法輸入)全部通過——確認 `//evil.com`/`https://evil.com`/`javascript:alert(1)` 都被擋回 `/`,合法的站內路徑(含 query string)原樣通過。完整的 OAuth 端對端往返(真的走 Google/Discord 登入流程)無法在腳本裡自動化測試,這點誠實記錄——跟這個 session 稍早 magic-link 瀏覽器測試放棄時的結論一致。

## 執行過程中的插曲

跑最終 `eslint`/`build` 驗證時,把 `cd ... && npx eslint ... &` 這個指令背景化執行,結果 `cd` 只作用在被背景化的子 shell 裡,沒有影響到後續同一個工具呼叫裡的 `npm run build`——導致 `build` 意外在 SoundArena repo 外層目錄執行,誤跑到使用者 home 目錄下一個完全無關的 `training-dashboard` 專案。發現輸出跟預期的 Next.js build log 對不上後立刻停下來查證,不是照單全收「exit code 0 就當作過了」,確認問題後重新在正確目錄跑過一次,拿到真正的 SoundArena build 結果。記錄這件事是提醒自己:背景化(`&`)的 shell 指令,`cd` 的作用範圍只到那個子 shell 為止,不會延續到後面的同步指令。

## 驗證總覽

`tsc`/`eslint`/`build` 全程乾淨(eslint 剩 2 個跟本次改動無關的既有既有警告)。SA-006(部分)、SA-007、SA-008、SA-013 都有真實 PoC 對正式環境驗證,SA-009 是純前端無障礙屬性改動,已用 tsc 確認所有呼叫點都正確傳入必填的 `label`。
